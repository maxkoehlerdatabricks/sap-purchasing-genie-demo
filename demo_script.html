1 · Genie One — ask in plain English before anything else 3 min

"Before I show you a single table, let me show you the end state. This is Genie — one place in Databricks where anyone can ask a question in plain English. No SAP screen, no report request, no analyst in the loop."
  1. SHOW the unified Genie landing page.
    There's one Genie — the audience doesn't have to know which space or table to pick. Point out that Genie can be pointed at the whole purchasing_demo schema, and that later in the demo we'll show two curated spaces plus a supervisor that route automatically.
    "Think of this as the front door. One box. Everything else we build today — the governed tables, the certified functions, the metric views, the supervisor — exists so that the answers coming out of this box are ones you can actually trust."
  2. TYPE the headline question in plain English: Which materials are single-sourced and their only supplier has a delivery-risk flag?
    The answer returns in seconds — a ranked list of the highest-priority supply-continuity risks. Expand "Show generated code" so they see Genie wrote and ran real SQL against Unity Catalog.
    "That's the $2M question — answered in seconds, by anyone, without waiting on a specialist. Now let me peel back the layers and show you why you can trust this answer."
  3. TYPE one quick follow-up to prove it's conversational: Which plants are affected?
    Genie keeps the context from the previous question and narrows the same result set — no re-stating the whole question.

3 · Catalog Explorer — the governed data model 4 min

Start in the Databricks UI left nav → Catalog.

  1. CLICK Catalog → serverless_stable_7qzrfp_catalog → purchasing_demo. Show the list of tables.
    "We simulated a realistic SAP purchasing landscape — 13 raw SAP tables — and consolidated them into 5 clean, analysis-ready 'gold' tables."
    The 5 gold tables the whole demo runs on. Walk the table below so the audience knows what each one contains and what a single row represents (the "grain").
    Gold tableGrain — what one row meansWhat it contains
    MATERIALOne material at one plant (MATNR + WERKS) Material master consolidated across MARA/MAKT/MARC: description, material type (MTART), material group (MATKL), MRP controller, procurement flags.
    SUPPLIEROne supplier in one purchasing org (LIFNR + EKORG) Vendor master across LFA1/LFB1/LFM1: name, country (LAND1), purchasing block flag (SPERM), company-code and purchasing-org attributes.
    SOURCINGOne approved material→vendor sourcing link at a plant (MATNR + WERKS + LIFNR) The source list + quota arrangement: which vendors may supply which material at which plant, the quota split (QUOTA), validity dates, and the derived IS_VALID_SOURCE flag.
    SUPPLIER_RISKOne risk assessment window for a supplier (LIFNR, time-sliced VALID_FROM..VALID_TO) Ariba-styled risk classification: risk category, numeric risk score, and the delivery-risk flag (DELIVERY_RISK_FLAG) with the dates it was active.
    PURCHASE_ORDEROne purchase-order line item (EBELN + EBELP) PO header + line + history flattened from EKKO/EKPO/EKBE: material, supplier, order date, net price (NETPR), requested vs goods-receipt date, and the derived ON_TIME_FLAG.
    VALUE_DICTIONARYOne business-term → SAP-code mapping (DOMAIN + CODE) Human labels for cryptic SAP codes (e.g. MTART 'ROH' = raw material, SPERM 'X' = blocked) so Genie can translate plain English to codes.
    The 13 RAW_* tables (MARA, MAKT, MARC, LFA1, LFB1, LFM1, EORD, EQUK, EQUP, SUPPLIER_RISK, EKKO, EKPO, EKBE) are the simulated SAP source; the gold tables above are what the demo actually queries.
  2. CLICK the SOURCING table → Overview tab.
    The table description and the column comments — every column is documented in business language (e.g. "IS_VALID_SOURCE = a valid, non-blocked source").
    "This is the heart of the model — which vendors are approved to supply which material at which plant, plus their quota split."
  3. CLICK the Sample data tab, then the Details / Relationships view.
    The primary key and the foreign key to MATERIAL. These constraints aren't just documentation — Genie uses them to join correctly.
  4. CLICK the View relationships button (top-right of the table's Overview) to open the Entity-Relationship (ER) diagram.
    Catalog Explorer auto-draws the ER diagram from the primary/foreign keys — SOURCING in the middle, joined out to MATERIAL and SUPPLIER, with SUPPLIER_RISK and PURCHASE_ORDER hanging off the vendor key. You can also reach it from the schema page → View relationships to see all 5 gold tables at once.
    "The star schema isn't in a slide — Databricks generates it live from the declared keys, so the diagram can never drift from the data."
  5. CLICK the Lineage tab on a gold table (e.g. SOURCING), then open the Lineage graph.
    The upstream RAW_* tables → the gold table → downstream consumers (the metric views, Genie spaces, and the App). Click a node to expand, and switch to column-level lineage to trace a single field (e.g. how IS_VALID_SOURCE is derived).
    "Every gold table carries automatic, end-to-end lineage — you can prove exactly which raw SAP fields feed a KPI, which is gold for audit and impact analysis."
    Note: external lineage in Databricks refers to bringing lineage from outside systems into Unity Catalog (e.g. from an external ETL tool or the source SAP system), so UC can show a connected picture that spans beyond Databricks — not just the lineage captured natively within the workspace.
  6. CLICK into Functions in the schema. Open e.g. materials_without_multisourcing.
    These are governed, parameterized SQL functions — "trusted assets." A business rule like "fewer than 2 valid vendors" is defined once, centrally, and reused everywhere — including by Genie as a certified answer.
  7. CLICK a metric view such as mv_delivery_performance and open its definition.
    "KPIs like on-time-delivery rate are defined once as a metric view, so every dashboard, Genie space, and app computes them identically. No metric drift."
Don't dwell on SQL here. The message is governance: documented tables, keys, certified functions, and consistent metrics — the foundation that makes the AI layer trustworthy.

7 · Under the hood — Agents, the Supervisor, provisioning & auth 3 min

This section is for the technical audience — it explains what we just demoed and how it is wired. Stay in the Agents area; refer back to the notebooks as needed.

What an "Agent" is in Databricks

An Agent is an LLM app that reasons and calls tools in a loop — SQL / UC functions, vector search, Genie spaces, or external APIs. Agents are authored with the Mosaic AI Agent Framework (ChatAgent / ResponsesAgent), logged to MLflow, registered in Unity Catalog, and deployed to a Model Serving endpoint.
"In Agent Bricks — the low-code path we used here — you declaratively configure managed agents instead of writing the framework code. Each Genie space acts as a specialist agent."

The Supervisor (Multi-Agent Supervisor / MAS)

The Supervisor is an orchestrator agent sitting above multiple sub-agents: it routes each request to the right one and synthesizes the answer. Here it supervises the two Genie spaces (PO Analytics vs Sourcing & Supplier Risk), deployed as a single endpoint (mas-655dcd32-endpoint). It speaks the Responses API ({"input":[{"role":"user","content":"…"}]}) and emits a function_call naming the routed sub-agent — which the App parses to show the "routed to …" badge.

Provisioning

Provisioning is declarative REST in 06_agent/06a_create_mas.py: POST /api/2.0/multi-agent-supervisors with {name, agents:[{name, description, agent_type:"genie", genie_space:{id}}], instructions}. The Genie space IDs come from the _GENIE_SPACES table (written by 05a). Databricks auto-provisions the serving endpoint; the notebook polls serving_endpoints.get(name).state.ready == READY (not the MAS tile status), and persists the endpoint name to _MAS_ENDPOINT.

Authentication

There are two auth boundaries:
  1. Caller → MAS endpoint: locally uses the CLI profile via WorkspaceClient(); in the deployed App it runs as a service principal with injected env, and the backend calls w.config.authenticate() to get a Bearer header (works for PAT / OAuth / SP with no code change — no hard-coded tokens).
  2. MAS / Genie → data: the Genie spaces use run_as_type: "VIEWER", so queries execute as the end-user's identity and per-user UC permissions are enforced.
"The trade-offs: least privilege — the endpoint only needs CAN QUERY plus UC grants. VIEWER run-as preserves per-user governance and audit, versus service-principal run-as which centralizes access but loses per-user enforcement. And a single MAS endpoint means one ACL choke point and a smaller blast radius."

8 · Observability — viewing MAS traces in MLflow 2 min

"Governance isn't just access control — it's being able to see exactly what the AI did. Every question the supervisor answers is captured as an MLflow trace."
Why: every MAS invocation is auto-captured as an MLflow trace (the Agent Framework auto-instruments MLflow Tracing) — showing the supervisor's routing decision (which Genie sub-agent), the generated SQL, the tool/span tree, latency, and token usage. Great for demonstrating governance and observability.
  1. CLICK Path 1 — Serving endpoint (primary): Machine Learning → Serving → open mas-655dcd32-endpoint → the Traces tab (a.k.a. inference logs / monitoring).
    Each row is one invocation; expand it to see the routing, the generated SQL, the spans, latency and tokens. Best for answering "why did it route here / what SQL ran?"
  2. CLICK Path 2 — MLflow Experiment: Experiments → open the experiment tied to the MAS deployment → the Traces tab.
    Inspect the full span tree (supervisor span → Genie sub-agent span → SQL execution span); filter by status/time to find failures or slow calls.
  3. CLICK Path 3 — Complementary: the exact SQL Genie ran also appears in Query History for warehouse 117d425266741646.
Demo tip: after asking the MAS a question in the App chat, switch to Serving → Traces to show the routing + SQL live, and tie it back to the function_call (the routed sub-agent name) that the app backend parses in app/backend/main.py.

9 · Authoring with AI — Notebook + Genie, SQL from a prompt, Visual Data Prep 8 min

Everything so far ran on the governed gold tables. This section shows that the people who author against those tables get the same AI assistance the business gets — three ways in: a notebook, the SQL editor, and a no-code canvas. These are quick concept demos, not a build step: each one is a small example that previews a result and writes nothing — no tables are created, so it's safe to run live and safe to re-run.

"You've seen the business ask questions in plain English. Now let me show you that the people building these datasets get the same AI assistance — whether they live in a notebook, the SQL editor, or a no-code canvas. I'll keep these small — just enough to show the idea, nothing saved."

9a · Prepare a dataset in a notebook with the Assistant

Left nav → Workspace → open a new (or scratch) notebook on serverless.

  1. CLICK the Assistant icon in the notebook (the sparkle in the cell toolbar / right-hand panel), or start a cell comment and press the assistant shortcut.
    The Databricks Assistant is context-aware — it already knows the tables and columns in purchasing_demo from Unity Catalog, so it writes code that references real column names, not guesses.
  2. TYPE a small plain-English prompt into the Assistant: Read supplier and supplier_risk from serverless_stable_7qzrfp_catalog.purchasing_demo, join on LIFNR, and show the 10 suppliers with the highest risk score — name, country, risk category, risk score. Just display it, don't save anything.
    The Assistant generates a PySpark cell — reading supplier and supplier_risk, joining on LIFNR, ordering by RISK_SCORE, and ending in .display(). Point out it picked the correct join key and columns because UC metadata grounds it.
    "I described the outcome in one sentence. The Assistant wrote correct PySpark against our real schema — because it's reading Unity Catalog, not hallucinating column names."
  3. RUN the cell.
    The result renders inline as a DataFrame preview — nothing is written to the catalog. This is purely to show AI-assisted authoring; there's no saveAsTable.
    If the Assistant panel isn't visible, enable Databricks Assistant in the workspace settings. You can also select the generated cell and use /explain to show it documenting the code, or /fix to show it debugging — not just generating.

9b · Write SQL from a prompt with the SQL editor's AI assistant

Left nav → SQL Editor. Pick the warehouse Serverless Starter Warehouse and set the catalog/schema to serverless_stable_7qzrfp_catalog / purchasing_demo.

  1. CLICK the Assistant (sparkle) in the SQL editor, or type a comment prompt and trigger inline generation.
    The same context-aware assistant, now producing SQL instead of PySpark. This is the analyst path — no Python needed.
  2. TYPE a small prompt: Show the 10 suppliers with the worst on-time delivery rate — join purchase_order to supplier, compute the average of ON_TIME_FLAG per supplier, worst first.
    The assistant writes a SELECT joining purchase_order to supplier, computing AVG(ON_TIME_FLAG) as the OTD rate, grouping per supplier and ordering ascending. Run it and show the result grid — a read-only SELECT, nothing persisted.
    "An analyst who knows the business but not the SAP schema just wrote a correct, two-table join by describing what they wanted. And it's real, editable SQL — nothing hidden."
  3. CLICK into the generated SQL and use the assistant to explain this query or also show each supplier's risk score.
    It iterates on the existing query — edit-in-place, not a black box. We stop at the result; we're not saving it. (If a governed team wanted to keep it, this is where they'd promote it to a view or certified function like the ones in section 3 — but that's not part of this demo.)
    Tie it back: this is exactly how the demo's certified functions (e.g. otd_rate_per_supplier) started life — a prompt in the editor, later promoted to a governed, parameterized function that Genie can call.

9c · Explore the same idea with Visual Data Prep (no code)

The third path is fully visual — for users who don't want to write PySpark or SQL at all. Open Visual Data Prep (the no-code data-preparation canvas — reachable from the + New menu / Data Ingestion & prep, or the transform canvas in the workspace).

  1. CLICK + New → the Visual Data Prep canvas and add a source step pointing at purchasing_demo.supplier_risk.
    A drag-and-drop transformation canvas — each step is a node (source, join, aggregate, filter, select), with a live data preview after every step. No syntax to learn.
  2. CLICK + Add step to join in supplier (on LIFNR), then add a filter step (e.g. DELIVERY_RISK_FLAG = 'X') and a sort by RISK_SCORE descending.
    Each step previews its output immediately, so a business user can see the join and the filter take effect before committing anything — self-service exploration with guardrails.
    "Same kind of question as the notebook and the SQL editor — the riskiest suppliers — but built by pointing and clicking. And it's reading the exact same governed tables. Three front doors, one foundation."
  3. SHOW the preview panel and stop there.
    We don't hit "Create table" — this is a concept demo, so we leave it at the live preview. Point out that if they wanted to, one click would materialize it as a governed UC table with full lineage — but we're intentionally persisting nothing today.
Depending on your workspace version the no-code prep surface may be labelled Visual Data Prep, a data-prep pipeline, or the Lakeflow visual editor. The message is the same regardless of label: a no-code path onto the same governed tables.
Nothing here is persisted. 9a ends in .display(), 9b is a read-only SELECT, and 9c stops at the preview — all three are safe to run live and safe to re-run. If short on time, demo just one of the three and pick the surface that matches your audience (engineer → notebook, analyst → SQL, business → Visual Data Prep).

10 · AI/BI Dashboard — a filter and two charts 3 min

Left nav → Dashboards → Create dashboard (AI/BI). This is a quick build to show that the same governed metric views also power point-and-click dashboards — no SQL for the author, and every number matches Genie and the app because it's the same metric definitions underneath.

"Chat is great for ad-hoc questions. But teams also want a standing view they check every morning. Let me build a small dashboard in a minute — one filter, two charts — straight on our governed metric views."
  1. CLICK the Data tab → add a dataset. Point it at the metric view mv_delivery_performance (and add mv_supplier_risk for the second chart).
    The author picks a governed metric view, not a raw table — so measures like OTD Rate are already defined once and can't drift. Mention you could also type a natural-language prompt here and let AI/BI draft the dataset.
  2. CLICK the Canvas tab → Add a filter widget. Bind it to Purchasing Org (from mv_delivery_performance).
    The one filter — a Purchasing Org dropdown. It's a dashboard-level filter, so it drives every chart on the page at once.
    "One control at the top. When a category manager picks their purchasing org, the whole page re-scopes to them."
  3. CLICK Add visualization → Chart 1: OTD trend. Choose a line chart: X = Receipt Month, Y = OTD Rate.
    On-time-delivery rate over time. Because OTD Rate is a metric-view measure, the chart just references it — the author writes no aggregation SQL.
  4. CLICK Add visualization → Chart 2: risk by country. Choose a bar chart on mv_supplier_risk: X = Vendor Country, Y = Delivery Risk Vendors.
    Where the delivery-risk vendors are concentrated. Two charts, one filter, zero hand-written SQL — all on the governed layer.
    "Now watch the filter tie it together." CLICK a value in the Purchasing Org filter and both charts re-scope live.
  5. SHOW (optional) Publish in the top-right.
    Publishing shares a read-only, governed view with the business — same permissions and lineage as everything else. We won't dwell here; the point is how fast a governed dashboard comes together.
A one-filter, two-chart dashboard is enough to make the point. If a dashboard already exists in the workspace, open it instead of building from scratch — the click path (filter → charts on metric views) is the same. Nothing here needs to be saved for the rest of the demo.

12 · Automation — running the pipeline as a Job 2 min

Left nav → Workflows → Jobs → open "sap_purchasing_data_prep."

  1. SHOW the job's Tasks tab.
    A single serverless task, data_prep, that runs the top-level 00_run_all orchestrator. No cluster is configured → it runs on serverless compute. Point out the base parameters (catalog, schema, warehouse_id) — the same Python variables that parameterize the manual run.
    "The job doesn't duplicate any logic — it just invokes the exact same orchestrator we run by hand, so the scheduled pipeline and the manual run stay in lock-step."
  2. CLICK Run now (top-right) to trigger a run, then open the Runs tab.
    The run list with status and duration. Click into a run to see the task graph, live logs, and the notebook output for each stage (raw → gold → semantics).
  3. SHOW (optional) Schedules & Triggers in the job's right-hand panel.
    "From here you'd add a cron schedule or a file-arrival trigger to refresh the gold layer automatically — the same notebooks, now hands-off."
The job is created/updated idempotently by 08_jobs/08a_create_jobs (Python SDK, by job name). If you don't see it, run that notebook once. To trigger from code instead of the UI, uncomment the run_now_and_wait cell at the bottom of that notebook.
